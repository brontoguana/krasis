# Gemma 4 INT4 on an 8 GiB GPU

The bounded profile supports the Gemma-4-26B-A4B-it architecture with native Rust/CUDA language and vision execution. Python loads and converts weights at startup and preprocesses images. Measurements use an RTX A6000 externally constrained to an 8 GiB device-wide allowance; physical 8GB-card performance is untested. This feature branch does not establish general release or independent whole-model numerical qualification.

Select the checkpoint in the launcher on a single GPU with at most 8 GiB, or explicitly select the profile:

```sh
./dev python -m krasis.server \
  --model-path /path/to/gemma-4-26b-a4b-it \
  --gemma-8gb --num-gpus 1 \
  --max-context-tokens 32768 --kv-cache-mb 512 \
  --no-enable-thinking
```

Authentication, binding and model acquisition follow the normal server workflow. The profile does not download model weights. On a larger GPU `--gemma-8gb` forces the profile; it does not impose a physical VRAM allowance. `KRASIS_GEMMA_8GB=0` explicitly selects the existing larger-memory path. The 32K default includes text, image tokens and generated output. Requests must also fit measured live memory while leaving at least 600 MiB free. The bounded server plans with at least 664 MiB free to cover transient driver/library allocations. Larger contexts require a sufficient explicit KV budget and remain subject to admission.

The profile uses INT4 routed experts (Marlin, group 128), HQQ4 attention (default group 128), INT4 dense MLPs and output head, and native streamed INT4 vision projections. Dense down projections use group 64 because their input width is 2,112. BF16 activations, normalization, small routing matrices, learned image position embeddings and the host token embedding retain their original semantics. The tied output projection has a separate INT4 representation; there is no retained full BF16 language-model source copy.

The authoritative BF16 token embedding is host-mapped. Packed dense/head matrices occupy about 629 MiB resident GPU memory. Routed experts stream from their existing source-backed packed cache. Vision has one pinned packed backing (about 316 MiB) and one device staging slab (about 45.4 MiB), rather than keeping its complete encoder on the GPU. The two-axis learned vision position table accounts for 45 MiB of the higher-precision host backing. Conversion is incremental, not a simultaneous full BF16 and packed model load.

INT4 weights are independent of KV precision. This profile uses k6v6 decode KV and BF16 prefill history. Revision `377ca2b` selects BF16 staging because an identical-ID, fixed-chunk experiment reversibly changes a failed retrieval digit when FP8/BF16 staging is alternated. The native planner charges the additional stage bytes. `KRASIS_GEMMA_PREFILL_STAGE_BF16=0` retains FP8 staging for diagnostics; it has demonstrated retrieval loss and is not the accuracy-qualified default. Staging precision is part of automatic/approved heatmap metadata, so calibration artifacts cannot silently cross these contracts. The existing k4v4 ring guard remains in place. Its 25 sliding-attention layers retain a 1,024-token mathematical window and bounded physical storage. The exact prefill stage keeps 32 additional rows for short chat-template rewinds; deeper branches require a suitable saved boundary or full prefill. The five full-attention layers retain full history. Export reconstructs complete canonical sliding windows before decode, with physical wrap and stage-specific conversion argument order handled explicitly.

One image per request is supported, resized by the checkpoint image processor to at most 280 soft tokens / 2,520 valid patches. Image token blocks remain intact across prefill chunks, and sliding image attention preserves its bidirectional mask. Square and rectangular images are tested. Image requests remain explicitly uncacheable, including follow-ups that resend the image. Text session restoration supports active GPU and pageable RAM boundaries. CUDA graph decode remains guarded for this ring profile; execution uses the native eager path.

Correctness revision `cc35ab5` repairs an in-place half-split RoPE race: each thread now owns both members of its pair in prefill, eager decode and the graph-position kernel. No serving workspace or global synchronization is added. Twelve fixed-plan requests across four fresh processes, with HCS enabled/disabled and cache reuse disabled, produce bit-identical complete prefill logits. Continuations repeat within each fixed HCS setting; cross-setting decode equivalence is not established. The original failed receipts remain preserved. CUDA regression checks include full/partial rotary widths and unchanged tails.

The independent vision discrepancy has a separate cause. The retained reference rounded its non-parameter rotary frequencies to BF16, supplied an all-true mask that changed SDPA dispatch, and used different FP32 normalization reductions. In the first tested norms, all 13–25 differing values are adjacent BF16 values extremely close to rounding midpoints. Independent CPU/FP64 equations validate these producers. Matching frequency/backend and substituting the native norm producers makes all 27 complete encoder blocks bit-identical for square and rectangular images (144,446,976 values); the complete pool/projector comparison passes its unchanged tolerance. Reverse input-norm substitution reproduces the reference Q/K/V exactly. This establishes causality, not an unconditional independent whole-encoder tolerance pass. The original backend-compatibility failure is retained; thresholds are unchanged. Earlier INT4-versus-BF16 feature cosine measurements around 0.94 remain bounded quantisation evidence, not broad visual-quality qualification.

The repaired public profile passes repeated original/changed image-and-code retrieval fixtures at 4K and 32K, image follow-ups, active/RAM text restoration, cancellation and reset. A 960×672 public image exercises exactly 280 processed soft tokens / 2,520 patches. Images remain uncacheable. An independent full source-BF16 Transformers model on the exact native IDs makes the same adjacent-only deduplication mistake as native INT4; both pass an explicitly global deduplication control. The earlier “BF16 dense/head control” still uses quantised experts, HQQ attention and k6v6 KV and must not be called a full BF16 model.

Latest evidence is in `krasis-internal/gemma4-correctness-236223/`; the preceding `gemma4-int4-8gb-236082/` directory preserves the original performance, memory and failed quality receipts. These are bounded correctness and practical-quality checks, not general release admission or an independent whole-language-model numerical qualification.

The repaired default profile retains 32K context and a 512 MiB KV budget. Three short 128-token completions sustain 21.91–21.94 tokens/sec; 32K image requests complete in 21.73–21.85 seconds. Observed minimum free memory is 704.1 MiB and host RSS peaks at 18.50 GiB including text-session snapshots. The earlier FP8-staging profile completed the corresponding image requests in about 17.7–17.9 seconds; those measurements remain preserved. The revised accuracy/default configuration trades some prefill speed and stage capacity for the demonstrated retrieval repair. Weight precision and host ownership are unchanged.

The final no-HCS 64K/BF16-staging probe executes within the allowance (at least 740.1 MiB observed free), but its changed-code fixture returns `X4P2-J6N1` instead of `X4P2-J6N3`. **32K is the validated fixture limit; 64K is runnable capacity with a failed quality gate.** Earlier 64K passes belong to the earlier staging configuration. The remaining 64K failure has not been attributed to a source-model limitation or independently qualified full-model arithmetic. Context expansion is deferred. The historical 96K quality failure and 128K admission refusal remain preserved; the existing guards are unchanged.

NVML sampling is complemented by native direct counters; sampling alone does not prove a transient allocation bound. Measurements use an A6000 constrained to 8 GiB, rather than physical 8GB hardware. Ordinary default timings precede a metadata-only identity addition; its seven CPU policy/identity tests pass, inference arithmetic/binary is unchanged, and final fresh-process checks use the final metadata source.

Higher-precision weight exceptions measured from the selected checkpoint are 1,476,395,008 bytes of host embedding, 21,803,520 bytes of routers/scales, 1,224,252 bytes of language norms/scalars and 47,447,136 bytes of vision positions/norms/std data. Runtime BF16 activations, required per-layer RoPE tables, k6v6 KV and transient scratch are additional. INT4 vision stages one projection at a time into BF16 contraction scratch; it does not keep a complete BF16 encoder resident. New dense/head conversion reached 16.67 GiB RSS while reusing existing expert/HQQ artifacts; a fully cold rebuild of all prior artifacts was not remeasured.

The advertised 280-token image boundary is now exercised publicly. Runtime identities include the changed CUDA/Rust dependencies; heatmaps must match the repaired runtime identity. Companion evidence retains original failures and the distinct runtime, backend-compatibility and practical-quality verdicts.
